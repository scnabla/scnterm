# scnterm 开发与维护步骤

## 项目目标与约定

基于官方 WezTerm 创建个人分支项目，按实际使用需求开发功能，并持续接收官方更新。功能设计兼顾其他使用者，个人偏好通过配置控制。

| 仓库暂定名称 | `scnterm` |
| 仓库地址 | `https://github.com/scnabla/scnterm` |
| 官方上游 | `https://github.com/wezterm/wezterm` |
| Git 提交邮箱 | `46028051+scnabla@users.noreply.github.com` |
| 个人终端配置仓库 | `https://github.com/scnabla/personal-config` |

仓库名称与本地目录名称分别管理，保留当前 `scnablaTerm` 目录。后续更名时单独更新远程地址、文档和构建发布引用；应用显示名称、可执行文件名称及安装包名称另行安排。

Linux 构建环境、命令及验证记录见 [开发环境](development-environment.md)。

## 第一阶段 搭建开发环境

阶段目标：取得官方源码，配置构建工具，完成一次未经功能修改的构建，并在目标系统启动运行。

### 1. 检查项目与构建主机

1. 检查项目目录、已有文件、Git 状态及适用的 `AGENTS.md`，保留现有文档和用户文件。
2. 首个构建目标为 Linux x86_64，在当前 Ubuntu 开发主机完成编译与运行验证。Windows 构建与验证在需要交付 Windows 版本时单独进行。
3. 检查构建主机的系统版本、磁盘空间、Git、Rust 和平台编译工具，记录已有版本，按所选源码版本的要求补齐依赖。
4. 使用共享 Windows 主机时，先读取 `windows-env` 技能，通过 `win11` 连接检查环境，在 Windows 本地磁盘构建。Linux 项目目录保留为开发工作目录，并明确两端源码同步方式及对应提交。
5. 保留日常使用的终端与配置，开发构建使用独立输出目录及测试配置。

### 2. 创建 Fork 并取得源码

1. 检查 GitHub 当前登录账户是否为 `scnabla`，确认 `scnterm` 是否已存在。
2. 从官方 `wezterm/wezterm` 创建 Fork，使用暂定名称 `scnterm`。已有仓库则核对其上游关系后复用。
3. 将源码放入 `/home/scnable/work/scnablaTerm`。该目录包含本计划，导入前检查与上游 `docs/` 文件的重名情况，保留已有文档；不要直接向非空目录执行克隆。
4. 将 `origin` 指向个人 Fork，将 `upstream` 指向官方仓库。保留官方提交历史及许可证文件。
5. 在项目内配置提交身份；在 Windows 等其他工作副本创建提交前同样检查邮箱。

在项目已经成为 Git 工作副本后设置本地提交身份：

```bash
git config --local user.name scnabla
git config --local user.email 46028051+scnabla@users.noreply.github.com
```

远程仓库预期值：

| 名称 | 地址 |
| --- | --- |
| `origin` | `https://github.com/scnabla/scnterm.git` |
| `upstream` | `https://github.com/wezterm/wezterm.git` |

### 3. 建立分支并确定构建版本

| 分支 | 用途 |
| --- | --- |
| `main` | 跟随官方主分支，不加入个人功能或项目专用文档提交 |
| `personal` | 保存项目专用文档和已完成的个性化改动，作为个人版本的构建来源 |
| `feature/<功能名>` | 从 `personal` 创建，开发单项功能 |
| `update/<日期>` | 从 `personal` 创建，验证一次官方更新 |

1. 核对上游默认分支名称；按上表建立分支，如上游名称不同则相应调整同步操作。
2. 首次构建从选定的官方提交开始，记录完整提交编号与关联版本或日期。
3. 阅读该提交中的官方构建说明、工具链声明、子模块配置和持续集成构建文件，确定依赖版本与构建命令。
4. 初始化所需子模块，安装或选择对应工具链。不要默认使用最新 Rust 替代源码要求的版本。
5. 将本项目文档保存在 `personal` 分支，保持应用源码与选定的官方提交一致后执行首次构建。

### 4. 编译与运行原始版本

1. 按选定源码版本的官方步骤构建，保存实际命令、日志与产物路径。
2. 如构建失败，先核对依赖、工具链、子模块和平台要求，记录错误及处理结果。
3. 从独立目录启动开发产物，先使用最小测试配置检查窗口打开、终端输入与退出。
4. 再使用适配目标系统的个人配置测试副本检查默认 Shell 启动、字体、背景图、窗格和快捷键；Windows 版本另行检查 PowerShell。
5. 测试操作限定在新启动的开发窗口，保留正在使用的终端会话。

### 5. 记录开发环境

完成首次构建后新增 `docs/development-environment.md`，记录以下可复现信息：

- 构建目标系统、CPU 架构与实际构建目录。
- 官方提交编号、个人分支提交编号及子模块状态。
- Git、Rust、平台编译器及 SDK 的实际版本。
- 依赖安装方式、完整构建命令、构建日志和产物位置。
- 独立启动方法、测试配置位置及运行结果。
- 如使用两台主机，记录源码同步方法和提交一致性检查方式。

第一阶段完成条件：源码与分支安排明确，提交邮箱正确，构建成功，产物可独立启动，基础输入和窗格操作通过，环境记录足以复现构建。

## 第二阶段 开发个性化功能

1. 按具体使用问题建立需求，写清触发步骤、现有行为、期望行为与验收方式。
2. 可由 Lua 配置实现的调整继续维护在 `personal-config`；需要改变程序行为的功能进入 `scnterm`。
3. 从 `personal` 创建功能分支，每次处理一项功能，提交保持小范围，避免混入无关格式化与重构。
4. 将个人偏好设计为可配置选项。程序默认值和公开示例不写入个人目录、私有主机地址、凭据或仅本机存在的资源路径。
5. 根据改动执行相关测试，并在真实开发窗口验证操作。通过后合入 `personal`，记录使用方式和对应提交。
6. 更换应用名称、图标及安装包标识作为独立任务处理，首次环境搭建不批量替换上游源码名称。

## 第三阶段 同步官方更新

1. 保存当前工作，记录正在使用的个人版本提交编号，并保留可运行的旧产物。
2. 获取 `upstream` 更新，将干净的 `main` 快进到选定的官方提交。出现分叉时先检查原因。
3. 从 `personal` 创建 `update/<日期>` 分支，将选定的上游提交合并到该分支。
4. 按功能处理冲突，保留上游修复和个人功能的预期行为。共享分支采用合并方式维护，不通过强制推送改写已共享历史。
5. 完成构建，执行受影响的测试，并检查常用终端操作。无文本冲突也需要验证运行行为。
6. 验证通过后合入 `personal`，记录此次上游提交、个人版本提交和测试结果，再生成供日常使用的产物。
7. 更新失败时保留现有个人版本，在更新分支继续处理；已发布版本出现问题时先使用上一份可运行产物。

常用操作检查范围：

- PowerShell 启动、命令输入、中文输入与复制粘贴。
- 字体、背景图、窗口拖动、最大化和全屏。
- 窗格创建、关闭、焦点切换、尺寸调整及正向内容轮换。
- 多窗格缩小再放大后的路径提示符重绘。
- 配置加载与重新加载。

## 第四阶段 提供他人使用

1. 提供通用默认配置，将个人配置作为独立示例或外部引用。
2. 保留上游许可证与版权声明，说明项目基于 WezTerm，以及个人版本增加的功能。
3. 每次发布记录个人版本号、上游提交、构建平台与使用方法，提供对应平台产物。
4. 对通用修复评估向上游贡献，已被上游接收后移除重复维护的改动。
5. 仓库更名后更新本地远程地址、文档链接和发布配置，同时单独检查应用名称及安装路径是否需要调整。
